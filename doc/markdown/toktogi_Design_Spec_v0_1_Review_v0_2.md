## 0. 적용 순서와 상태 정의

### 0.1. 적용 순서

이번 사용자의 확정 사항을 이전 명세와 이전 검토의 제안보다 우선한다. 다음 우선순위는 **같은 사항에 대한 충돌이 있을 때** 적용한다.

1. 이번 사용자의 항목 1~7 확정 메시지.
2. 그 결정을 정확하게 정리한 이 보고서의 확정 항목.
3. 결정과 충돌하지 않는 원본 명세와 기존 검토 내용.
4. 이 보고서의 추가 구현 제안.

새 제안이 사용자 결정을 대신하지 않는다. 특히 항목 6은 명시적으로 보류되어 있으므로 Normal 공간·시점 선택·Depth 변환을 이번 개정에서 임의 확정하지 않는다.

### 0.2. 상태 구분

| 표시 | 의미 |
|---|---|
| **확정** | 사용자가 채택한 정책·기능·표현 방향 |
| **부분 확정** | 상위 결정은 끝났지만 수치·함수·범위·구현 방식은 남음 |
| **보류** | 사용자가 추후 결정한다고 명시한 사항 |
| **개선 제안** | 확정 요구를 구현하기 위한 제안. 아직 추가 승인을 받은 규칙은 아님 |
| **검증 대기** | 실제 에셋·코드·대상 장치에서 확인하지 않음 |
| **재선택 불필요** | 같은 상위 질문을 다시 물을 필요가 없음. 하위 기술 결정은 남을 수 있음 |

P0/P1/P2는 이전 보고서의 의미를 유지한다. P0는 관련 구현이나 대량 제작 전에 필요한 선결 조건이며, 확인된 실행 오류를 뜻하지 않는다. 정책이 확정된 경우에는 ‘채택 여부 미정’ 지적을 종료하고, 필요한 기술 계약과 시험만 남긴다.

### 0.3. 이번 개정으로 더 이상 미정이 아닌 것

실시간 재질 반응 채택, 외부 라이브러리·SDL 접근·최종 렌더러 교체의 허용, 기본 고정 카메라와 캐릭터 회전, 픽셀풍, 도약의 이동 속도 합산, 제동 기능, 착지 회복 중 성능 축소, 탄성 표면의 타이밍 도약, Capsule 형상은 다시 선택할 대상이 아니다.

반면 ‘모두 허용’은 모든 OS를 지원하거나 모든 라이브러리를 동시에 사용한다는 뜻이 아니다. 대상 환경·주력 렌더러·실제 의존성은 아직 선택하지 않았다.

## 1. 사용자 확정 사항 7개와 잔여 범위

| 결정 ID | 확정 내용 | 기존 검토에서 변경하는 부분 | 남은 범위 |
|---|---|---|---|
| **DEC-01 / 항목 1** | 실제 조명에 대한 재질 반응은 필수. 일부 자산, 예를 들어 배경은 베이크 재질·그림자 허용. | ‘사전 외관만으로 충분한가’ 질문 종료. 전체 A0 전환을 동일 요구의 대체안으로 보지 않음. | 재조명 자산 목록, 베이크 허용 자산·광원·그림자 범위 |
| **DEC-02 / 항목 2** | 외부 라이브러리, SDL 계층 직접 접근, 렌더러 교체를 포함한 이전 항목 2의 선택 범위를 모두 허용. | 금지 여부에 의한 B1/B3 제약 종료. B1만을 먼저 완성해야 하는 순서도 고정하지 않음. | 기준 장치·OS·버전, 채택 라이브러리, 최종 출력 담당 |
| **DEC-03 / 항목 3** | 기본은 고정 카메라에 캐릭터 회전. 카메라 회전 확장 고려. 화풍은 픽셀풍. | 일반 렌더와 픽셀풍의 상위 선택 종료. 카메라 회전을 설계에서 배제하지 않음. | 논리 해상도·표시 크기·촬영 각도·방향 수·회전 범위·추적 정책 |

| **DEC-05 / 항목 5** | 캐릭터는 Capsule 충돌 사용. 지지 시 다리 끝이 바닥에 닿게 설정. | 충돌 프록시 형상 선택 종료. 접지 기준을 캐릭터 몸 중심이 아니라 발의 시각적 위치와 연결. | 캡슐 축·반경·높이·루트 오프셋, 가장자리 지지·skin·접촉 허용 오차 |
| **DEC-06 / 항목 6** | 스프라이트·좌표·Normal·Depth·앵커 대응은 추후 결정. | 이전 개선안의 특정 변환을 승인된 규칙으로 취급하지 않음. | 해당 좌표·방향 데이터 계약 전부. 관련 양산 관문 유지. |
| **DEC-07 / 항목 7** | 실시간 재질 반응을 채택. 이전 항목 7의 Metallic/Roughness를 포함한 반응 계산 대상임. | L2 계열 재질 반응 채택 여부 질문 종료. | 정확한 BRDF 변형, Roughness 변환·하한, 광원·감쇠·노출·톤 매핑 |

**DEC-01과 DEC-07의 결합:** 주요 실시간 재질에는 Normal과 Roughness/Metallic 등에 맞는 반응이 필요하다. 배경 등에 베이크를 허용했다고 해서 캐릭터까지 모두 완성 이미지로 대체할 수 있다는 뜻은 아니다. 반대로 모든 자산에 모든 맵을 강제로 저장하거나, 살아 있는 캐릭터에 금속·발광 능력을 넣는다는 뜻도 아니다.

**DEC-03과 DEC-06의 결합:** 캐릭터가 회전한다는 기획은 확정되어 있다. 그것을 몇 방향의 이미지와 어떤 벡터 변환으로 구현할지는 아직 보류다.

## 2. 기존 검토 28개 항목의 갱신 상태

이 표는 이전 보고서의 RV ID를 유지한다. ‘잔여’는 기능 채택 질문을 다시 여는 것이 아니라, 채택한 기능을 구현할 기술 규칙을 가리킨다. 기존 수치 계산은 당시 가정에서의 계산이며, 새 정책 아래의 최종 성능으로 승계하지 않는다.

|---|---|---|---|
| **RV-01** | 채택 여부 종료 / 적용 범위 잔여 | 실제 반응 필수 + 일부 베이크. 전체 A0만으로는 합격 불가. 자산별 품질·예외 선언 필요. | DEC-01·07 |
| **RV-02** | 허용 여부 종료 / 환경·구현 잔여 | 외부·SDL·교체 모두 가능. 기준 장치와 출력 경로를 선택하고 실제 동작 검증. | DEC-02 |
| **RV-03** | 합산·제동·회복 정책 확정 / 수식 잔여 | 기존 속도 합산, 입력 제동, 회복 중 축소, 탄성 도약을 반영하여 궤적·정지 거리를 재검증. | DEC-04 |

<a id="r03"></a>
## 3. 실제 재질 반응과 베이크 병행

### 3.1. 합격 기준 변경

**[확정]** 실제 재질 반응은 필수다. 일부 배경의 베이크 허용은 성능과 제작을 위한 예외이며, 전체 게임을 사전 조명 이미지로 대체하는 허용이 아니다.

따라서 기존 A0/B1 선택 질문은 다음과 같이 바뀐다.

| 기존 질문 | 개정된 질문 |
|---|---|
| 사전 렌더 외관만으로 만족할 수 있는가? | 실제 반응이 필요한 자산과 베이크를 허용할 자산을 어떻게 나눌 것인가? |
| B1이 느리면 전체 A0로 낮출 것인가? | 실제 반응을 유지하면서 대상·해상도·연산 경로를 어떻게 조정할 것인가? |
| 외부 GPU 출력 교체가 허용되는가? | 허용된 후보 중 어떤 출력 경로를 실제 채택할 것인가? |

실시간 반응은 실제 상승 장면에서도 확인해야 한다. 별도 재질 교정실만 동작하고 코스는 전부 고정 이미지라면 새 요구를 만족했다고 처리하지 않는다.

### 3.2. ‘베이크’를 세 종류로 구분

| 종류 | 저장하는 것 | 실행 중 처리 | 이 설계와의 관계 |
|---|---|---|---|
| **재질 데이터 베이크** | Base·Normal·ORM 등 표면 데이터 | 조명과 시선으로 다시 계산 | 3D→2D 실제 반응의 기본 제작 방식 |
| **정적 조명 성분 베이크** | 정적인 간접광·차폐·그림자 등 | 필요한 동적 성분과 구분하여 결합 | 선택적 혼합. 중복 조명 방지 계약 필요 |
| **완성 화면 색 베이크** | 이미 조명된 최종 배경·소품 이미지 | 정해진 상태로 표시 | 사용자 허용 범위에 해당하는 일부 배경 등에 적용 |

‘원본 머티리얼을 베이크했다’는 말만으로 실시간 반응 여부가 결정되지는 않는다. 이미 빛이 들어간 완성 색을 Albedo처럼 다시 조명하여 명암을 이중 적용하지 않는다. 이 구분은 [R1 §4~7]의 데이터/출력 구분을 이어받는다.

### 3.3. 자산 분류의 적용안 — 목록은 아직 확정 아님

| 자산 | 우선 검증할 방식 | 비고 |
|---|---|---|
| 플레이어 개체 | 실제 재질 반응 | 회전·포즈·광원 변화가 동시에 드러나는 대표 대상 |
| 젖은/마른 돌, 주요 착지면 | 실제 재질 반응 우선 | 플레이 판단에 필요한 대비를 실제 코스에서 시험 |
| 탄성 잎 | 실제 반응 또는 명시된 혼합 | 변형·접촉 타이밍과 재질 데이터가 일치해야 함 |
| 먼 배경·비상호작용 장식 | 완성 이미지 베이크 가능 | 강한 이동 광원 반응을 약속하는 위치에는 그대로 사용하지 않음 |
| 고정 환경의 정적 그림자 | 베이크 가능 | 그림자를 만든 물체·광원이 고정이라는 전제 기록 |
| 움직이는 캐릭터·잎의 그림자 | 별도 근사 또는 동적 처리 비교 | 움직이는 대상의 예전 그림자가 배경에 영구 남지 않게 함 |

위 대상 분류는 요구를 구체화하기 위한 **개선 제안**이다. 사용자가 배경을 예로 든 것이 모든 배경은 베이크, 모든 소품은 재조명이라고 확정한 것은 아니다.

### 3.4. 혼합 경계 검토 — RV-29

베이크 예외마다 다음을 기록하는 구조를 제안한다.

```text
material_evaluation: runtime / baked_final / mixed_components
baked_components: 어떤 조명·그림자·간접광이 이미 포함되었는가
runtime_components: 어떤 광원·재질 반응을 실행 중 계산하는가
light_scope: 어떤 자산에 어떤 광원이 영향을 주는가
shadow_source: baked_static / dynamic / contact_approximation / none
```

이 명칭은 프로젝트용 필드 제안이며 라이브러리 API가 아니다. 다음 조건을 시험한다.

- 같은 광원을 베이크와 실시간 계산 양쪽에서 중복 반영하지 않는다.
- 움직이는 빛이 가까운 캐릭터에는 크게 작용하지만 바로 옆 필수 발판에는 아무 효과가 없는 장면이 의도적인지 점검한다.
- 동적 캐릭터의 그림자가 고정 배경에 미리 박혀 있지 않도록 한다.
- 베이크 배경은 색공간·노출·픽셀 밀도·광원 방향이 동적 자산과 시각적으로 이어져야 한다.
- 베이크 허용은 충돌·가림 데이터 생략 허용이 아니다. 밟거나 앞뒤로 가리는 지형은 별도 정보를 유지한다.
- 카메라 회전을 나중에 켤 때 한 장의 배경이 모든 시점을 제공한다고 가정하지 않는다.

그림자 전체를 실시간으로 만드는 요구는 이번에 확정되지 않았다. 재질 반응과 그림자 갱신 정책을 별도로 다룬다.

### 3.5. 구현 경로의 재평가

| 경로 | 개정 후 역할 |
|---|---|
| **A0: Pico2D 기본 이미지 출력만** | 참조 이미지·베이크 자산·디버그 비교에 사용 가능. 전체 게임의 실제 반응 요구를 단독 충족하는 경로로 간주하지 않음. |
| **A1: 표준 Python + SDL 직접 연결** | 허용된 후보. 구현 비용·성능 검증 후 채택 여부 결정. |
| **B1: Pico2D + 배열 연산 + SDL 업로드** | 허용된 실제 반응 후보. CPU 계산과 업로드를 포함한 장면 비용으로 판단. |
| **B2: GPU 계산 결과를 다시 Pico2D로 전달** | 허용된 연구 후보. 전송·동기화 비용까지 확인. |
| **B3: GPU 렌더러가 최종 출력** | 사용자 허용 범위 안의 후보. 교체 허용 여부를 다시 묻지 않아도 되지만, 실제 채택은 아직 미정. |

**[개선 제안]** 동일한 작은 픽셀풍 자산으로 B1과 B3 중 필요한 후보를 짧게 비교한 뒤, 주력 출력 담당을 하나로 좁힌다. 모든 경로를 완성 수준으로 만들 필요는 없다. 기존 B1 우선 권고는 현재의 필수 제약이 아니다. 어느 후보의 성능이나 API 호환성도 이번 문서에서 확인 완료로 처리하지 않는다.

## 4. 고정 카메라·캐릭터 회전·픽셀풍

### 4.1. 확정 범위

**[확정]** 화풍은 픽셀풍이다. 일반 렌더와 픽셀풍 중 어느 쪽을 제품으로 삼을지 다시 비교하지 않는다. 일반 렌더 원본은 제작 중간 결과·고증·재질 비교용으로 사용할 수 있다.

**[확정]** 기본은 고정 카메라에서 캐릭터가 회전하는 구성이다. 카메라 회전 확장도 고려한다.

**[미정]** 고정이 카메라 각도만 뜻하는지 화면 위치까지 뜻하는지, 추적·줌을 허용하는지는 별도다. 기존 35°·45°·640×360·8방향 등은 승인된 최종 수치가 아니라 이전 시제품 제안으로 남는다. 카메라 회전 범위가 360°인지, 제한 각도인지, 구간 전환인지도 확정하지 않는다.

### 4.2. 픽셀풍 안에서 남는 제작 선택

저해상도 직접 렌더와 고해상도 후축소, 수작업 픽셀 정리, 팔레트·디더링·윤곽선의 방식은 비교할 수 있다. 단, 색상용 팔레트 처리를 Normal·Depth·ORM에 그대로 적용하지 않는다는 데이터 원칙은 유지한다. [R1 §3·8]

해상도는 다음 세 가지를 분리하여 정한다.

| 구분 | 예 |
|---|---|
| 원본 출력 해상도 | Blender가 만드는 각 프레임의 픽셀 수 |
| 논리 화면·캐릭터 표시 크기 | 게임에서 캐릭터와 발판이 실제로 차지하는 논리 픽셀 |
| 최종 창 배율 | 논리 화면을 실제 모니터에 확대하는 비율 |

정수배 확대·nearest 샘플링은 유력한 초기 비교안이다. 이것만으로 모든 카메라 이동과 재질 하이라이트가 안정되는 것은 아니므로, 서브픽셀 이동·다리 끝·반사 깜빡임을 따로 확인한다.

### 4.3. 카메라 확장에 대비하되 구현을 선확정하지 않음

물리 방향, 카메라 방향, 프레임/view 선택을 코드 책임상 분리해 두는 것은 개선 제안이다. 해당 필드의 정확한 기준축·벡터 변환은 DEC-06에 따라 보류한다.

고정 카메라에서도 캐릭터가 회전하므로 방향 스프라이트 정합 문제는 남는다. 카메라 회전을 나중에 추가하면 배경·발판의 다른 시점, 가림 순서, 빛과 노멀의 관계도 함께 검증해야 한다. 따라서 ‘확장 고려’와 ‘이미 회전 지원 완료’를 구별한다.

## 5. 속도 합산·제동·착지 회복

### 5.1. 속도 합산 원칙

**[확정]** 도약은 기존 이동 속도를 버리고 새 속도로 대체하지 않는다. 기존 이동 성분에 도약으로 추가되는 속도 성분을 더한다.

정의를 분리한 개념식은 다음과 같다.

```text
v_takeoff = v_carry + delta_v_jump + delta_v_elastic
```

- `v_carry`: 발사 순간까지 이어받을 기존 이동 속도.
- `delta_v_jump`: 충전·조준·회복 상태를 반영한 도약 추가 성분.
- `delta_v_elastic`: 탄성 조건을 만족할 때만 생기는 추가 성분.
- 위 식은 구조 설명이다. 계수·차원별 처리·상한은 미정이다.

**아직 정하지 않은 중요한 부분:** 착지 직전의 하강 속도를 그대로 `v_carry`로 사용할지, 접촉을 해결한 뒤의 속도를 사용할지, 어떤 성분을 보존할지다. 사용자는 ‘기존 이동 속도 합산’을 확정했지만 수직 충돌 처리와 샘플 시점까지 정하지는 않았다.

**[개선 제안]** 다음 세 순간을 별도로 기록한다.

```text
v_incoming       접촉 직전 속도
v_after_contact  접촉·착지 감쇠를 처리한 속도
v_takeoff        도약 추가 성분을 더한 최종 속도
```

하강 속도의 일부를 탄성 에너지로 바꾸는 모델을 채택할 경우, 그 값을 일반 속도 합산·반발·별도 보너스에서 여러 번 중복 사용하지 않도록 한다.

### 5.2. 제동

**[확정]** 제동 기능은 존재한다.

**[미정]** 제동 입력, 접지/회복/공중 중 적용 상태, 표면별 감속값, 순간 정지 허용 여부, 반대 입력이 감속 뒤 방향 전환으로 이어지는 규칙.

제동 가능을 ‘공중 자유 조향 승인’이나 ‘공중 제동 금지’로 확대 해석하지 않는다. 둘 다 이번 결정에서 확정되지 않았다. 속도 합산을 검증할 때에는 제동을 켠 경우와 끈 경우를 분리한다.

### 5.3. 착지 회복

**[확정]** 착지 회복 중에는 이동 속도와 재도약 범위가 정상 상태보다 줄어든다. 회복을 이유로 모든 이동·재도약을 일괄 금지하는 이전 구현 해석은 사용하지 않는다.

| 항목 | 확정된 효과 | 남은 구현 선택 |
|---|---|---|
| 이동 | 정상 상태보다 축소 | 최대속도·가속·현재 관성 속도 중 무엇을 얼마나 제한할지 |
| 재도약 | 정상 상태보다 범위 축소 | 추가 수평/수직 속도, 충전 한도, 회복 경과에 따른 비율 |
| 회복 종료 | 정상 성능으로 복귀 | 고정 시간·접촉 충격량·연속 접지 중 어떤 기준인지 |
| 제동 | 기능과 함께 일관되게 동작 | 회복 중 제동 세기·우선순위 |
| 탄성 성공 | 별도 범위 증가 기능 존재 | 회복 제한과의 조합 순서 |

**중요한 설계 검토:** 기존 이동 속도를 더하기 때문에, 점프 추가 성분만 줄여도 총 이동 범위는 여전히 클 수 있다. 따라서 ‘회복 상태에서 범위 축소’를 검증할 때는 같은 진입 속도·조준·지면을 기준으로 정상 상태와 비교한다. 단순히 파라미터 이름에 `reduced`를 붙이는 것으로 완료하지 않는다.

탄성 타이밍 성공은 일반 회복 중 재도약과 따로 검증한다. 회복 제한을 무시하는지, 제한 후 보너스를 붙이는지, 전용 발사값을 쓰는지는 §6의 잔여 결정이다.

### 5.4. 기존 도약 거리의 재해석

기존 약 5.18u는 이동 속도를 상속하지 않은 조건의 계산값이다. 합산 정책에서는 이를 ‘최대 도약거리’로 고정할 수 없다. [D0 §4.3·4.4], [R0 §4.1]

아래는 기존 제안값 `도약 추가 속력 10.5u/s, 각도 55°, 중력 20u/s²`를 그대로 사용한 **산술 예시**다. 기존 이동 속도는 수평만 있고, 출발·도착 높이는 같으며, 탄성·제동·회복 축소·공기저항·속도 상한은 생략한다. 이 값들을 새 밸런스로 승인한 것은 아니다.

| 기존 수평 속도 | 합산 후 수평 속도 | 같은 높이까지의 수평 변위 | 변위 크기 |
|---|---|---|---:|
| 정지 | (6.023, 0)u/s | (5.180, 0)u | **5.180u** |
| 도약 방향으로 2u/s | (8.023, 0)u/s | (6.900, 0)u | **6.900u** |
| 도약 반대 방향으로 2u/s | (4.023, 0)u/s | (3.460, 0)u | **3.460u** |
| 도약 방향과 직각으로 2u/s | (6.023, 2)u/s | (5.180, 1.720)u | **5.458u** |

수직 추가 속도는 약 8.601u/s, 같은 높이까지의 시간은 약 0.860초다. 직각 진입에서는 조준 방향과 실제 합성 궤적이 다르다.

**개선안:** 조준 화살표가 입력 방향만 뜻하는지, 합산 후의 실제 이동 방향까지 보여주는지 구분한다. 레벨 도달성 검사에는 출발 위치뿐 아니라 진입 속도 벡터를 포함한다.

### 5.5. 연속 속도 증가 — RV-31

같은 방향의 기존 속도를 계속 합산하고 접촉·제동·저항에서 충분히 줄이지 않으면 반복 도약으로 속도가 증가할 수 있다. 이것은 실제 무한 가속이 발생했다는 측정 결과가 아니라, 추가된 규칙에서 검증해야 하는 가능성이다.

다음 중 무엇을 채택할지는 미정으로 둔다.

- 접촉 시 속도 보존율 또는 감속.
- 상태별 속도 상한.
- 탄성 보너스 상한·포화.
- 연속 입력·접촉에 대한 발동 제한.
- 빠른 속도를 허용하되 코스와 충돌 검사를 그 범위에 맞추는 방식.

제동만으로 사용자가 항상 속도를 줄인다고 가정하지 않는다. 충돌·카메라·저장·회복 시험에는 제동을 하지 않는 연속 도약도 포함한다.

## 6. 탄성 표면의 착지 동시 도약

### 6.1. 채택된 기획

**[확정]** 나뭇잎처럼 게임에서 탄성이 있다고 정의한 표면에 착지하면서 도약 타이밍을 맞추면, 도약 범위가 증가한다.

이것은 실제 종에서 정량 검증된 협동 추진·반사 능력이 아니라 사용자에게 승인된 게임 규칙이다. 모든 잎이 똑같은 탄성을 갖는다는 자연 법칙으로 설명하지 않는다. 탄성은 게임의 물리 프로필에 명시하며, Roughness나 Metallic에서 자동 계산하지 않는다. [D0 §2·6.2], [R2 §6·15]

### 6.2. 기존 착지 상태의 변경

기존의 단일 `AIRBORNE → LANDING → 회복 완료` 흐름만으로는 새로운 기능을 표현하기 어렵다. 다음 상태 구분을 **개선 제안**으로 둔다.

```text
AIRBORNE
  └─ 유효한 발판 접촉
       ├─ 탄성 표면 + 유효한 타이밍 도약 명령
       │      → 탄성 도약 발사 → AIRBORNE
       └─ 그 외
              → LANDING_RECOVERY
                   ├─ 제한된 이동·제동
                   ├─ 축소된 범위로 재도약 → AIRBORNE
                   └─ 회복 종료 → NORMAL_SUPPORTED
```

위 명칭과 분기는 구현 제안이다. 탄성 발사의 구체적인 입력 처리·회복 우선순위까지 확정한 것은 아니다.

모든 접지 상태에서 실제 지지가 사라지면 공중 상태로 전환해야 한다. 이때 남은 충전값이나 타이밍 예약만으로 허공 도약을 만들지 않는다.

### 6.3. ‘동시에’의 판정 — RV-30

동시성을 화면에 표시된 한 프레임과 동일시하지 않는 방향을 권한다. 사용자 입력과 실제 접촉 시각을 물리 시간에서 비교하는 식으로 구현하면 렌더 FPS 변화와 분리하여 시험할 수 있다.

```text
time_error = accepted_jump_command_time - landing_contact_time

허용 후보:
    -pre_window <= time_error <= post_window
```

이는 수식의 형태를 제안한 것이며, 시간 창의 폭·대칭 여부·허용 입력은 아직 정하지 않는다.

| 잔여 결정 | 이유 |
|---|---|
| ‘도약 명령’이 누름인지 놓음인지 | 기존 충전-해제 입력과 연결해야 함 |
| 착지 전 예약을 허용할지 | 반응 타이밍과 재도전 난이도가 달라짐 |
| 착지 후 어느 정도까지 동시로 볼지 | 회복 중 일반 재도약과 경계가 필요 |
| 공중에서 충전을 준비할 수 있는지 | 기존 기본 조작에서 추가되는 능력 |
| 누른 채 착지해도 성공인지, 새로운 입력이 필요한지 | 입력 유지로 자동 연쇄되는지 결정 |
| 착지 직후 발사 힘을 어디서 얻는지 | 충전량·전용 최소값·고정값 등 중 선택 필요 |

‘버퍼 입력 허용’은 아직 확정하지 않는다. 다만 한번 채택한 타이밍 규칙은 30/60/120 렌더 제한 등에서 같은 물리 입력 결과를 내는지 시험해야 한다.

### 6.4. 회복 축소와 탄성 보너스의 관계

사용자 결정은 두 기능을 모두 포함하지만, 합성 순서는 지정하지 않았다. 다음은 서로 다른 선택지다.

| 후보 | 동작 | 차이 |
|---|---|---|
| 제한 후 보너스 | 회복으로 축소한 도약에 탄성 추가 | 보너스가 회복 축소를 얼마나 상쇄하는지에 따라 최종 범위가 달라짐 |
| 타이밍 성공은 전용 발사 | 정상/회복 도약과 별개의 탄성 발사 함수 | 성공의 차별성이 명확하지만 별도 밸런스 필요 |
| 타이밍 성공만 회복 예외 | 성공 시 회복 제한 일부를 생략하고 보너스 적용 | 일반 회복 입력과 우선순위가 분명해야 함 |

**이번 개정에서는 어느 후보도 최종 선택하지 않는다.** 구현 전에 하나를 골라 일반 회복 도약과의 기준을 문장·식·시험으로 연결한다.

‘도약 범위 증가’는 동일한 조건의 비보너스 도약보다 증가해야 한다. 증가시킬 대상이 수평 거리, 수직 도달 높이, 또는 둘 다인지는 남은 결정이다. 성공음을 내는 것만으로 범위 증가가 구현된 것으로 처리하지 않는다.

### 6.5. 한 접촉에서의 중복 방지

**개선 제안:** 실제 착지 사건마다 식별자를 부여하고, 그 사건에서 탄성 발사 명령은 한 번만 소비되도록 한다.

다음 경우가 별도 위험이다.

- 접촉 콜백이 한 틱에 여러 번 발생.
- 같은 발판의 여러 파트가 각각 접촉 보고.
- 미세한 들뜸으로 접지/공중이 반복.
- 탄성 반발 처리 뒤 일반 도약 처리가 다시 실행.
- 저장/복원 뒤 이미 소비한 입력이 재생.
- 렌더 애니메이션 프레임의 반복이 다시 충격량을 발생.

단순히 모든 접촉 틱마다 ID를 바꾸는 방식으로는 미세 들뜸 재발동을 막지 못한다. 새로운 착지로 인정할 최소 분리·접촉 종료 조건도 정해야 한다.

### 6.6. 탄성 잎의 움직임은 별도 선택

탄성 보너스가 존재한다고 해서 정교한 유연체·스프링 물리가 필수는 아니다. 초기에는 고정된 지지면에 눌림/펴짐 애니메이션과 게임용 보너스를 붙여 검증할 수 있다.

그러나 그림상 잎 윗면이 크게 내려갔는데 캡슐과 다리 끝은 원래 높이에 남으면 떠 보인다. 두 방법을 구분한다.

| 방법 | 정합 조건 |
|---|---|
| 지지면 고정, 시각 변형만 사용 | 실제 접지점 주변은 크게 어긋나지 않게 만들고 의도한 근사 범위를 시험 |
| 지지면도 움직임 | 발판 높이·속도·개체 지지·도약 속도 상속까지 함께 갱신 |

둘 중 무엇을 사용할지는 미정이다. 노멀맵만 움직여 실제 충돌 지형이 변한 것으로 취급하지 않는다.

### 6.7. 데이터 추가 제안

```text
surface.physics.elastic_enabled
surface.physics.elastic_profile_id
actor.recovery_remaining
actor.pending_jump_command
actor.landing_event_id
actor.elastic_command_consumed
```

세부 타입·이름·기본값은 후속 스키마에서 정한다. 광학 재질 ID와 탄성 프로필 ID는 분리한다. 금속처럼 보여도 탄성이 없을 수 있고, 비금속 잎에도 탄성이 있을 수 있다.

## 7. Capsule 충돌과 다리 끝 접지

### 7.1. 확정된 것과 미정인 것

**[확정]** 캐릭터 콜리전은 Capsule을 사용한다. 지지 상태에서 다리 끝이 바닥에 닿도록 루트·모델·표시 위치를 맞춘다.

| 결정됨 | 아직 결정되지 않음 |
|---|---|
| 캡슐형 충돌체 | 캡슐의 축 방향·반경·전체 길이 |
| 다리 끝 기준 접지 | 캡슐과 몸통·다리의 상대 오프셋 |
| 회전 캐릭터에 대응 | 캡슐이 함께 회전하는지, 수직 캡슐로 회전 불변인지 |
| 접지의 시각적 정합 필요 | 모서리 지지식, 발별 접촉 판정, 경사·움직이는 발판 처리 |

Capsule 채택이 다리마다 물리 콜라이더나 실시간 IK를 반드시 사용한다는 뜻은 아니다. 이를 추가할지는 별도의 구현 선택이다.

### 7.2. 수직 Capsule을 쓰는 경우의 배치 예 — 미확정 제안

수평 발판 중심의 첫 코스에는 월드 수직축 캡슐을 우선 비교할 수 있다. 반경 `r`, 반구를 포함한 전체 높이 `H`를 사용할 때 `H >= 2r`이어야 한다. `H=2r`은 구 형태의 퇴화한 경우다.

발판 높이가 `z_s`이고 별도의 skin 오프셋을 생략하면 다음과 같이 배치할 수 있다.

```text
capsule_center_z = z_s + H / 2
lower_segment_endpoint_z = z_s + r
upper_segment_endpoint_z = z_s + H - r
capsule_lowest_z = z_s
```

이 수식은 수직 캡슐 배치의 예시이며, 사용자가 축과 크기를 확정했다는 뜻이 아니다. 가로축 캡슐을 택하면 다른 변환이 필요하다.

### 7.3. 다리 끝이 닿도록 하는 제작 계약 — RV-32

캡슐을 둥근 몸통에만 맞추고 별도 발 오프셋을 무시하면 접촉 높이와 그림의 발끝이 어긋날 수 있다. 다음 기준점을 분리하는 것을 제안한다.

| 기준점 | 역할 |
|---|---|
| `physics_root` | 월드 위치·충돌체 배치의 기준 |
| `visual_root` | 프리렌더 이미지의 피벗과 연결되는 기준 |
| `foot_contact_plane` | 정상 지지 상태에서 다리 끝이 닿는 기준 평면 |
| `stance_foot_markers` | 각 프레임에서 실제로 지지하는 다리 끝의 위치 |

월드 접촉 위치를 먼저 결정한 뒤, 해당 상태의 시각 루트를 그 접촉면에 맞춘다. 크롭이나 방향 전환 때문에 물리 위치를 바꾸지 않는다.

걷는 동안 들어 올린 다리까지 모두 바닥에 붙이라는 뜻은 아니다. 대기·착지·지지 프레임에서 **현재 지지 역할을 하는 다리 끝**을 검사한다. 단차나 모서리에서 실제 지지가 없는 다리까지 공중의 바닥에 접촉한 것처럼 보이게 하지 않는다.

단순 평면의 한 프레임은 항목 6의 최종 좌표 계약 전에도 교정용으로 시험할 수 있다. 다방향·애니메이션 전체의 접지 정합은 항목 6 확정 뒤 통합 시험이 필요하다.

### 7.4. 캡슐이 결정해 주지 않는 것

캡슐과 발판이 조금 겹쳤다고 항상 안정 지지가 성립하는 것은 아니다. 게임에서 원하는 기준을 별도로 정한다.

- 중심/발 기준점이 유효 영역 안에 있어야 하는지.
- 접촉 법선과 지지 허용 각도.
- 넓은 몸통의 옆면 접촉을 착지로 잘못 분류하지 않는지.
- 얇은 잎의 아래쪽과 옆면을 어떻게 처리하는지.
- 목표 ‘안정 접지’에 허용하는 속도·시간·영역.
- 틱 내 여러 접촉의 우선순위와 허용 오차.
- 캡슐 크기를 변경하는 애니메이션을 허용할지.

따라서 RV-04는 ‘형상 미정’ 부분만 종료하고, 지지·충돌 해결 규약은 계속 열린 상태로 둔다.

## 8. 항목 6 보류와 항목 7 채택의 경계

### 8.1. 항목 6 — 보류를 유지

이번에 확정하지 않는 것은 다음과 같다.

| 영역 | 보류 내용 |
|---|---|
| 방향 선택 | 연속 캐릭터 각도와 이산 view의 연결, 경계 흔들림 처리 |
| 노멀 공간 | 객체/카메라/월드 공간 중 최종 방식과 변환 행렬 |
| Depth | 사용할지 여부, 기저·부호·단위·범위·위치 복원 |
| 피벗·앵커 | 2D/3D 좌표의 역할, 크롭·회전·발 접촉 변환 |
| 카메라 회전 | 선택 view 갱신, 배경 교체, 재투영·가림 정책 |

이전 보고서의 `sim_heading/render_heading` 분리와 왕복 투영 시험은 계속 검토할 수 있는 제안이다. 사용자가 ‘추후 결정’이라고 했으므로 이를 이미 승인한 데이터 계약으로 바꾸지 않는다.

### 8.2. 보류 중 진행 가능한 작업과 제한

| 진행 가능 | 최종 계약 전에는 완료 처리하지 않을 작업 |
|---|---|
| 독립적인 Capsule·도약·제동·회복 시험 | 다방향 캐릭터 전체의 Normal·Depth 정합 |
| 한 고정 포즈·한 고정 시점의 재질 교정 | 회전 카메라의 최종 지원 |
| 잠정 데이터로 최소 GPU/CPU 비교 | 최종 manifest와 대량 에셋 내보내기 |
| 탄성 타이밍을 회색 상자로 검증 | 모든 방향의 다리·결속 앵커 정합 |

잠정 데이터에는 실험용임을 표시하고 대량 생산 계약으로 사용하지 않는다. 보류 때문에 프로젝트 전체가 멈출 필요는 없지만, 관련 작업을 검증 완료로 표시해서도 안 된다.

### 8.3. 항목 7 — 실제 재질 반응은 채택

Normal에 따른 방향성 반응과 Roughness/Metallic의 반사 차이를 구현할 목표는 확정한다. 단순 밝기 배수나 고정 하이라이트 교체만으로 해당 목표를 충족했다고 판단하지 않는다.

그러나 다음 세부사항은 아직 선택하지 않았다.

| 계산 항목 | 남은 결정 |
|---|---|
| BRDF | 사용할 미세면 분포·기하 감쇠·Fresnel 조합 |
| Roughness | perceptual 값의 변환, 최솟값, 필터·축소 정책 |
| 금속·비금속 | 기본 반사율, 확산 성분 처리 |
| 광원 | 종류·강도 단위·감쇠·영향 반경 |
| 색 출력 | 선형화, 노출, 톤 매핑, 픽셀풍 색 단계 적용 순서 |
| 부가 효과 | IBL·Bloom·동적 그림자·Height/Depth를 어디까지 쓸지 |

GPU 렌더러로 교체한다고 이런 데이터·셰이딩 계약이 자동으로 결정되지는 않는다. 반대로 동적 재질 반응을 채택했다고 해서 모든 고급 효과를 구현할 필요도 없다.

### 8.4. 유지·보완하는 색공간 규약

이전 보고서 RV-10의 검사 문구 수정안을 유지한다.

> Base Color·Emissive 등 색상 채널은 선언된 색공간에 맞게 선형화한다. Normal·ORM·Height·Depth·coverage는 수치 데이터로 처리한다. 픽셀풍 색 단계 조절은 수치 맵 자체의 의미를 훼손하지 않는 위치에서 수행한다.

위 문구는 이 검토 개정본에 반영했다. 원본 명세서 AST-02의 파일 자체는 이번에 직접 수정하지 않았으므로 다음 통합 개정 시 교체해야 한다.

### 9.1. 교체해서 읽어야 할 핵심 문장

**재질 목표**

> 게임의 주요 대상에는 실제 조명 반응을 적용한다. 일부 배경·정적 조명·그림자는 베이크를 허용하며, 자산별 적용 범위를 기록한다. 베이크 경로만으로 게임 전체의 실시간 재질 반응 요구를 완료 처리하지 않는다.

**표현과 카메라**

> 화풍은 픽셀풍이며, 고정 카메라에서 캐릭터가 회전하는 구성을 기본으로 한다. 카메라 회전 확장을 고려하되, 시점·노멀·깊이·앵커의 최종 좌표 계약은 후속 결정으로 남긴다.

**이동과 탄성**

> 도약 속도는 기존 이동 속도와 도약 추가 성분의 합으로 결정한다. 제동을 제공하고, 착지 회복 중에는 이동 속도와 재도약 범위를 줄인다. 탄성 표면에서 착지와 유효 도약 입력이 맞으면 도약 범위가 증가한다. 입력 허용 시간·보너스 식·회복과의 우선순위는 별도 구현 계약으로 확정한다.

**접지**

> 캐릭터는 Capsule 충돌체를 사용한다. 지지 상태의 다리 끝이 바닥에 닿도록 물리 루트·시각 루트·프레임 피벗을 맞춘다. 캡슐의 크기와 지지 기준은 형상 채택과 별개로 정한다.

### 10.2. 판정 순서 제안

동일 틱에 착지·도약 입력·회복 상태 변화가 겹치는 경우, 처리 순서가 결과를 바꾼다. 다음 순서를 한 후보로 시험할 수 있다.

1. 이동 구간에서 실제 첫 접촉과 접촉 시각을 결정한다.
2. 그 접촉을 유효한 착지인지 분류한다.
3. 접촉 직전/직후 속도를 구분해 보관한다.
4. 도약 입력과 접촉 시각의 관계를 판정한다.
5. 선택한 회복·탄성 우선순위에 따라 **발사 한 번**을 결정한다.
6. 남은 물리 시간의 이동을 처리한다.
7. 결과 상태에 따라 그림·소리·이펙트를 표시한다.

이 순서는 검토 제안이며 아직 엔진 코드나 확정된 상태 전이표가 아니다.

## 11. 미정 사항과 결정 시점 갱신

### 11.1. 지금 다시 물을 필요가 없는 사항

- 실제 재질 반응을 쓸지: **사용한다.**
- 외부 라이브러리·SDL·렌더러 교체를 허용할지: **허용한다.**
- 일반 렌더와 픽셀풍 중 무엇을 쓸지: **픽셀풍이다.**
- 기본 카메라가 자유 회전인지: **기본은 고정이며 캐릭터가 회전한다. 카메라 회전 확장을 고려한다.**
- 기존 이동 속도를 버릴지 더할지: **더한다.**
- 제동·회복 중 축소·탄성 동시 도약을 넣을지: **넣는다.**
- 캐릭터 충돌체 형상: **Capsule이다.**

## 12. 개정된 구현 순서

| 단계 | 할 일 | 필요한 결정/증거 |
|---|---|---|
| **U0 결정 반영** | DEC-01~07을 요구 추적표에 연결. 전체 A0 대체·일반 화풍 미정·속도 대체·회복 완전 잠금 문구 제거 대상 표시. | 이 보고서의 확정/보류 구분 |
| **U1 환경·최소 출력 비교** | 허용된 후보 중 필요한 경로만 작은 재질 장면으로 비교. | 기준 장치와 실제 출력 담당 선택, 기능·비용 로그 |
| **U2 이동·캡슐 시험** | 회색 상자에서 합산·제동·회복 축소·기본 접지를 시험. | 속도/지지 계약과 Capsule 프로필 |
| **U3 탄성 타이밍 시험** | 한 탄성 발판에서 성공/실패·회복·중복 발사를 검증. | 입력 창·우선순위·보너스 함수 |
| **U4 한 포즈 픽셀 재질** | 한 시점의 캐릭터·돌·베이크 배경에서 L2와 혼합 경계 시험. | 픽셀 크기·셰이딩·범위 정의. 임시 좌표는 실험 표시 |
| **G-COORD** | 사용자 보류 항목 6을 후속 시점에 결정. | 좌표·view·Normal·Depth·앵커 계약. 보류 중 양산 완료 금지 |
| **U5 통합 시제품** | 다방향 픽셀 자산, 탄성 잎, 발 접촉, 실제 조명과 베이크 배경을 합침. | 접지·재질·회전·도달성·저장 통합 시험 |
| **U6 대량 제작·확장** | 기본 코스 양산. 카메라 회전·결속은 범위를 정한 뒤 추가. | 선행 검증 통과, 예산·결정 기록 |

물리 시험과 한 시점 재질 교정은 일부 병행할 수 있다. 정확한 좌표 정책을 보류했다고 모든 실험을 중단하지 않는다. 반대로 실험용 임시 좌표가 작동했다는 이유만으로 보류된 정책을 확정한 것으로 처리하지 않는다.

**바뀐 최소 결합 장면:** 픽셀풍 톡토기 한 개체, Capsule, 일반 발판과 탄성 잎, 실제 조명에 반응하는 가까운 재질, 베이크 배경 한 장. 기본 시점은 고정이고 캐릭터 회전은 단계적으로 검증한다. 물리·재질·접지 중 하나의 성공만으로 전체 완료를 주장하지 않는다.
